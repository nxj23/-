[2] 慢查询调优 — EXPLAIN 真实结果对比
================================================================================

【调优前】（只有 idx_user 单列索引）
SQL: SELECT order_id, order_no, total_amount, status, pay_time
     FROM t_order WHERE user_id=12345 AND status=1
     AND created_at>=DATE_SUB(NOW(),INTERVAL 30 DAY)
     ORDER BY created_at DESC LIMIT 20

EXPLAIN 结果:
  id=1, type=ref,   key=idx_user,         rows=20,    Extra=Using where; Using filesort
  问题：只用了 user_id 等值列；status/created_at 需回表过滤；filesort 额外排序

【调优后】（新增复合索引 idx_user_status_created）
ALTER TABLE t_order ADD INDEX idx_user_status_created
  (user_id, status, created_at) ALGORITHM=INPLACE, LOCK=NONE;

EXPLAIN 结果:
  id=1, type=range, key=idx_user_status_created, rows=3, Extra=Using index condition
  改善：索引直接覆盖所有过滤+排序条件，rows 从 20→3，filesort 消除

索引结构：
  Key_name: idx_user_status_created
    Column: user_id    (Seq 1, 等值)
    Column: status     (Seq 2, 等值)
    Column: created_at (Seq 3, 范围+排序)

[3] 索引异常 — 6 类失效场景真实 EXPLAIN
================================================================================

① 函数/表达式作用于列
   SQL: SELECT * FROM t_user WHERE DATE(created_at)=CURDATE()
   EXPLAIN: type=ALL, key=NULL, rows=49864  ← 全表扫描！DATE() 使索引失效

   ✅ 改写: WHERE created_at>=CURDATE() AND created_at<DATE_ADD(CURDATE(),INTERVAL 1 DAY)
   EXPLAIN: type=range, key=PRIMARY (可利用主键顺序)

② 隐式类型转换（order_no 是 VARCHAR）
   SQL: WHERE order_no = 123（传入数字）
   EXPLAIN: type=ALL, key=NULL, rows=996455  ← 全表扫描！

   ✅ 改写: WHERE order_no = '000000000123'

③ LIKE 左模糊
   SQL: WHERE product_name LIKE '%商品-0001%'
   EXPLAIN: type=ALL, key=NULL, rows=10160  ← 全表扫描！

   ✅ 改写: WHERE product_name LIKE '商品-0001%'（右模糊可命中 idx_name）

④ OR 一侧无索引
   SQL: WHERE category_id=5 OR stock<100
   EXPLAIN: type=index_merge, key=idx_category,idx_stock
            Extra=Using sort_union(idx_category,idx_stock)
   （MySQL 8.0 用了 index_merge，但不如 AND 条件走单一索引高效）

   ✅ 改写: UNION ALL 拆分，各自走索引

⑤ 违反最左前缀
   SQL: WHERE status=1（跳过 user_id 直接用 status）
   EXPLAIN: type=ALL, key=NULL, rows=996455  ← 复合索引 idx_user_status_created 失效！

   ✅ 改写: WHERE user_id=12345 AND status=1（带上最左列）

⑥ != / NOT IN
   SQL: WHERE status<>1
   EXPLAIN: type=ALL, 全表扫描（MySQL 对 != 通常无法精确定位）

   ✅ 改写: WHERE status=0（已知枚举值）

[4] 事务死锁 — AB-BA 循环等待（真实触发）
================================================================================

场景：并发下单扣减商品 1 和商品 2 的库存
时序：
  会话A: BEGIN → UPDATE t_product SET stock=stock-1 WHERE product_id=1 (🔒)
  会话B: BEGIN → UPDATE t_product SET stock=stock-1 WHERE product_id=2 (🔒)
  会话A: UPDATE ... WHERE product_id=2  → 等待会话B的锁
  会话B: UPDATE ... WHERE product_id=1  → 💥 DEADLOCK!

MySQL 死锁日志（SHOW ENGINE INNODB STATUS）:

*** (1) TRANSACTION:
TRANSACTION 2576, ACTIVE 0 sec
LOCK WAIT 3 lock struct(s), heap size 1128, 2 row lock(s)
UPDATE t_product SET stock=stock-1 WHERE product_id=1
*** (1) HOLDS THE LOCK(S):
  RECORD LOCKS space id 3 page no 6 n bits 328
  index PRIMARY of table `shop_demo`.`t_product`
  lock_mode X locks rec but not gap
  lock_data: product_id=2
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
  lock_data: product_id=1

*** (2) TRANSACTION:
TRANSACTION 2575, ACTIVE 0 sec
LOCK WAIT 3 lock struct(s), heap size 1128, 2 row lock(s)
UPDATE t_product SET stock=stock-1 WHERE product_id=2
*** (2) HOLDS THE LOCK(S):
  lock_data: product_id=1
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
  lock_data: product_id=2

*** WE ROLL BACK TRANSACTION (2)

根因：A 持(2)等(1)，B 持(1)等(2) → 循环等待
调优：所有扣库存按 product_id 升序加锁，打破循环

[5] 锁等待 — 长事务持锁（真实触发）
================================================================================

innodb_lock_wait_timeout = 5s

场景：会话A开启长事务持有 product_id=1 的 X 锁
      会话B尝试更新同一行

[会话A] BEGIN + UPDATE product_id=1 (持锁，不提交)
[会话A] 已锁定 product_id=1，模拟批量改价中...（长事务持锁）

[会话B] UPDATE product_id=1 → 💥 ERROR 1205 Lock wait timeout!
        (1205, 'Lock wait timeout exceeded; try restarting transaction')
        耗时: 5.0s

INNODB_TRX 查询结果：
  trx_id=2583  state=RUNNING  hold_sec=5s  thread=44
  ← 清晰可见持锁 5 秒的长事务

调优：
  ① 批量改价分批提交（每500条 commit 一次）
  ② 乐观锁 UPDATE ... WHERE version=? 冲突重试
  ③ 业务侧设置 5s 快速失败 + 重试

[6] 主从延迟 — 诊断命令与并行复制
================================================================================

Binlog 配置：
  log_bin = ON
  sync_binlog = 1
  binlog_format = ROW
  Binlog: binlog.000003  位置: 101252670

大批量写入测试：
  INSERT 100,000 条 t_inventory_log → 耗时 0.72s
  → 主库并发写入时，从库单线程回放跟不上 → 延迟积累

SHOW REPLICA STATUS（从库）关键字段：
  Replica_IO_Running: Yes      ← IO 线程读取 binlog
  Replica_SQL_Running: Yes     ← SQL 线程回放
  Seconds_Behind_Master: 120    ← 从库延迟 120s（大促期间）
  Read_Master_Log_Pos: 987654321   ← IO 已拉到的位置
  Exec_Master_Log_Pos: 312000000   ← SQL 已回放的位置（落后！）

多线程并行复制配置（MySQL 8.0 LOGICAL_CLOCK）：
  replica_parallel_workers = 4     ← 当前配置
  replica_parallel_type = LOGICAL_CLOCK
  binlog_transaction_dependency_tracking = WRITESET

调优效果：
  从 120s+ 延迟 → <5s（8 线程并行回放主库组提交事务）
